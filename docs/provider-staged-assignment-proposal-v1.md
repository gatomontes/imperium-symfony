## C1 — exact post-establishment assignment scope, including replacement

### C1.1 Chosen route and historical boundary

Add a distinct `imperium.staged-assignment-scope/v1` original and explicit v2 authority/assessment/application adapters. The original `imperium.operator-bootstrap-policy/v1` remains the **founding policy**. Do not edit it, reinterpret its target references, manufacture a second founding, or present a projected scope as its signed bytes. Its complete original sources must have existed at admission; any generic target there remains generic historical evidence and receives no native mapping credit.

The founding policy governs access, base selection, founding, candidate universe, workload, requirements, selection algorithm, caps and expiry. After same-root R4 completion and real native designation plus independent appointments, the new scope admits exact native mapping originals and governs a separate finite assessment/application branch. Historical old targets and old permitted sets are not silently replaced: the new signed scope expressly authorizes its own exact target pair and sets. Old v1 consumers continue their old behavior; only explicit version-aware consumers may follow the new branch.

The first stage requires no previous application, no started legacy W1/W2/W3 claims, completed original `found-augur`, completed R4, current original Augur holder and a quiescent v4 ledger. Selecting the staged branch irreversibly closes new legacy assessment/application progression for that root. This is a one-way branch choice, not a rollback/reset. Historical replay and outstanding settlement remain available. Existing installations with legacy applications are unsupported for this migration; no live migration is included.

### C1.2 Closed authority and scope shape

The existing enrolled Operator is the sole staged admission/application signer. Introduce a separate signed domain `IMPERIUM_OPERATOR_STAGED_ASSIGNMENT_V1` and envelope schema `imperium.operator-staged-assignment-act/v1`. It has exactly the existing Act payload fields (`schema`, `domain`, `instance_id`, `citadel_id`, `trust_fingerprint`, `issuer`, `effect`, `object_digest`, `policy_ref`, `expected_head`, `issued_at`, `expires_at`, `nonce`) and `signature`. Here `policy_ref` is always the admitted founding policy, never null. Ed25519 signs canonical payload bytes; preserve the original envelope and object bytes and their separate full SHA-256 values.

Only two effects are legal in this domain:

- `AUTHORIZE_BOOTSTRAP_POLICY`: authorizes exactly one staged scope, not a second founding policy. The current enrollment must include this effect **and** `AUTHORIZE_BOOTSTRAP_ASSESSMENT`, `ADMIT_BOOTSTRAP_EVIDENCE`, `APPLY_BOOTSTRAP_ASSIGNMENTS`. Approval of C1 explicitly grants this narrowly defined successor meaning to this new domain. An old-domain signature cannot be converted into a staged grant.
- `APPLY_BOOTSTRAP_ASSIGNMENTS`: authorizes exactly one initial mode-B application or one replacement, using the application terms below. It requires the corresponding current enrollment competence and cannot authorize scope admission.

The scope is a standard digest-bearing H record, with exactly these body fields:

Internal commissioned output references are not invented as pre-existing sources.

Permitted bindings must be a subset of the corresponding original role's permitted bindings. ### C1.3 Retention, activation, identity and atomicity

A new scoped admission owner retains exact raw signed scope and reachable support in the existing admitted-source custody, preserving first-admission lineage and all existing source limits. It authenticates enrollment, new domain, exact object, canonical root/instance/Citadel, expected current head, all current prerequisites and native originals before one journal publication. This is the explicit successor to the old signed-terms restriction, **not** an exception inside v1 `Admission::signedTerms`.

`imperium.onboarding-authority-state/v5` adds a migration record, scope history and a derived current-stage index. The migration retains the entire original v4 state, exact predecessor head and digest within the existing 8 MiB migration bound. All original maps, nonces, claims, custody, amounts, sequence lineage and applications survive. No second incumbent registry or private accepted-state installation is permitted. Scope history is authoritative; an absent, forged, missing-middle or divergent index refuses. Reconstructing an index must not create authority.

Nonce uniqueness is root/enrollment-wide across both domains. New acts and receipts must participate in existing admission/act/revocation custody and its 4,096 limit; new sources count toward 8,192. Exact completed replay returns historical recognition without reactivation or current authority. Same nonce with different original bytes, object, support or meaning refuses. A new scope consumes its branch/generation entitlement exactly once; assessment and application consumption are distinct and remain explicit. No latest-pointer publication before its complete original and application commit.

The existing `REVOKE_BOOTSTRAP` owner gains only lookup/validation support for exact retained staged-act nonces. The signer remains the current competent enrolled Operator. Revocation of a scope act invalidates its unconsumed operations and current usability of descendant applications; revocation of an application act invalidates that application's use. Existing issuer/policy withdrawal also fences the entire staged branch. Withdrawal is terminal, durable and does not erase receipts or refund budgets. There is no new general revocation API or bootstrap enrollment authority.

### C1.4 Assessment chronology and cumulative bounds

Frozen input includes both founding policy reference and scope reference, stage generation, exact holder, workload, candidate universe, target originals and evidence. Source originals exist at admission; later outcome links are resolved only from actual completed custody.

Add versioned scope-aware input/claim/group/outcome/assessment-view records; do not pass the scope as a forged policy to `AugurAdapter::resolveContext`. Scope and original policy references must both survive prepare, reservation, custody, response parse, settlement, selection, application and settings revalidation. There is **one attempt per group per scope**, strictly W1→W2→W3. No retry after failure, UNKNOWN, timeout, unresolved custody or cancellation. The actual retry allowlist remains `[]`. Only a successfully applied preceding stage permits another scope, and that scope must name at least one genuinely changed current mapping/Profile or independently appointed holder generation. A fresh scope cannot repeat a failed assessment or renew an unchanged pair. New-stage W1/W2/W3 is expressly authorized by a new exact Operator signature; old retry slots are never represented as that authority.

Across legacy and staged records together, retain original ceilings: 12 cognition attempts, 13 external requests including the one access call, 1,200,000 micro-USD total, 100,000 per attempt, 720,000 ms aggregate cognition, 730,000 ms aggregate requests, 60,000 ms per attempt, concurrency 1, 16,384 input/4,096 generated tokens, original response/parser limits. Stage maximum four is an additional bound, not an entitlement to unused exposure. Root-wide accounting includes reserved, unsettled, failed and completed exposure under existing settlement rules; admitting another policy/scope, changing sequence or using a canonical path alias cannot replenish it. Original lifetime and evidence freshness are not extended. If the real original policy has no remaining current budget/window, refuse; renewal is outside this proposal.

### C1.5 Initial application and successor replacement

An application receipt `imperium.staged-assignment-application/v1` retains exactly `founding_policy_ref`, `scope_ref`, `assessment_view_ref`, `previous_application_ref`, `authority`, `prior_assignments`, `next_assignments`, `consumed_effect_ids`, `commit_head`. The view binds all three actual original outcomes and their custody, original selection rule, complete candidate/role rankings, full predicate derivation and exact selected permitted pair. The existing selection algorithm remains unchanged. The scope current-stage index is derivable navigation metadata only; it is not a second source of incumbent authority. Advancing a scope does not itself supersede the latest completed application: existing settings remain usable under their own original scope only while all their own currentness obligations still hold. Structural PASS declarations alone cannot fill the native fitness derivation.

For initial mode A, derive one application entitlement from the current signed scope's exact finite set and successful assessment view. Its authority variant is `scope_effect`, carrying the retained scope act/admission and exact derivation references; it is not an old `policy_effect`. Initial mode B requires the additional staged-domain signed application act. Replacement requires that additional act in both modes. Signed application terms contain exactly `scope_ref`, `assessment_view_ref`, `expected_application_ref`, `prior_assignments`, `next_set_digest`; all match the current completed assessment and original pair. The act uses a distinct nonce and current expected head; admission alone never applies it.

Replacement is supported only within the staged lineage. It requires fresh native preparation/seal and complete findings/approval/qualification when the immutable Profile changes, current successor designation, separate independent appointment, fresh exact mapping/fitness originals, a new admitted scope and all three fresh successful assessments. An unchanged Seat may retain its exact original mapping and still must pass fresh whole-pair currentness checks. A holder-generation change alone changes the exact mapping and requires this same new scope/assessment/application path. Changed model/configuration may select only an already admitted founding candidate; anything outside that fixed universe needs another proposal.

Before the one application publication, revalidate current authority, whole pair, all native originals, C2 fitness, current assessment custody, exact predecessor, budgets and fresh expected head under the same owner. Advance both assignment-setting generations in one receipt even if one tuple's native identity is unchanged. Never rewrite a Profile or conflate binding generation, designation generation, holder generation, scope generation and settings generation. Neither designation nor appointment updates persistent settings automatically. A successor appointment can make old settings temporarily unusable while replacement awaits assessment; there is no fallback to the old holder.
