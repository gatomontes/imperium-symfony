# Provider Binding Activation integrity — Blackquill review

## Verdict

`REMEDIATION_REQUIRED_BEFORE_CREDENTIAL_PLATFORM_SELECTION`

The terminal custody refusal is correct. It does not prove that the activation corridor surrounding
that refusal is complete, reachable or safe to preserve unchanged. The campaign assembled exact
activation authority before establishing that its indispensable custody successor could exist.
Those records grant no execution authority, but they are now stranded and must not become prestige
evidence for a route that remains impossible.

## Findings requiring preparation

1. **Activation-principal reachability is unproved.** The caller-authority issuer requires
   `provider_binding_activation_authority` on an active Imperator runtime principal. No canonical
   producer, installation transition or lifecycle for that field is evident in the current runtime.
   A validator for an authority nobody can lawfully receive is architecture-shaped taxidermy.
2. **New-consumer interruption recovery is unproved.** Caller authority consumption is durable and
   forward-recoverable for the same consumer, but the Batch 2 decision and issuance routes persist
   their target records after that separate consumption. Their exact crash cuts, retry inputs,
   expiry interaction and conflict posture were not demonstrated for these consumers.
3. **Activation artifacts are stranded.** Batch 2 authorities and Batch 3
   `ACTIVATED_UNCONSUMED` leases cannot advance on the rejected credential substrate. Their expiry,
   quarantine, reconstruction and non-reinterpretation posture needs an explicit terminal policy.
4. **Credential-reference handling needs an exact boundary.** The feasibility service receives the
   capability object and reads its clear `credentialRef` to compare a digest. It does not persist
   the reference, but “not persisted” is weaker than “not exposed.” The authorized process,
   lifetime, memory and exception/logging boundary must be stated and tested.
5. **The cross-process proof is partly declarative.** A distinct broker instance refuses the exact
   object and `supportsCrossProcessCustody()` returns `false`. That honestly describes the current
   implementation, but it is not yet a crash/restart or second-process demonstration. The evidence
   must distinguish architectural impossibility, declared posture and experimentally observed loss.

## Non-finding

The review does not recommend manufacturing custody from metadata, serializing the capability,
reissuing it, reopening the live command or weakening the terminal refusal. Any remediation that
does so has failed before it begins.
