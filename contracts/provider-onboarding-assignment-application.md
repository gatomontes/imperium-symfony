## Scope and ownership

Apply the complete model/configuration/Profile tuple pair for `courtyard.courtthane` and `clavium.locksmith`, persist it, resolve it after restart, and support explicit authorized operator change and revalidation. These are model settings, not personnel appointments. Do not create an occupant, Profile approval, commission, credential, Curia, or Augur replacement as a consequence of settings application.

The authoritative commit point is the existing `FormationJournal` aggregate under its existing lock. `CommandLedger` owns command/step/slot consumption. `AuthorityStore` retains original evidence and current authority; `AssessmentGroups` resolves linked outcomes. At entry, `StateValidation` rejects nonempty `applications` and `assessment_views`; `CurrentAuthority` only derives the dynamic founding rule; `CommandLedger` refuses assignment effects. Those are actual missing seams, not implemented capabilities.

Declare the new internal record schemas, closed field sets, bounds, map keys, exact predecessor references, source graph, and producer/consumer ownership in a design note before coding. Extend those existing owners explicitly. Any state extension requires a bounded explicit version/migration, preservation proof for all retained original bytes and prior consumption, idempotent migration, and refusal of malformed/unknown versions. No migration on preview/read; no nested public journal calls inside a locked callback; no second assignment/consumption journal.

## Persistent resolution and explicit change

Add a production resolver that reads the authoritative aggregate under its existing inspect boundary, verifies original application/receipt/history and returns the exact persisted role/model/configuration/Profile tuple and generation. Specify and test the actual model-settings consumer boundary. `FormationPersonnel::currentCourtthane/currentLocksmith` remain personnel authority checks; `FormationSessionAuthority` and `FormationCognition` still require their separate officer/session/lease authority. The legacy `DeepSeekSymfonyPlatformAdapter` is not itself an onboarding settings producer. A narrow consumer adapter is allowed where indispensable, with compatibility proof and unchanged service configuration; do not silently activate global wiring.

Once applied, settings persist until an explicit competent operator change. Model unavailability, credential refresh, catalogue changes, expiry, revocation or a different recommendation cannot silently substitute or erase them. Distinguish historical assignment recognition from current eligibility for a new operation. Currentness failure blocks affected use while preserving history. Settings never grant dispatch authority.

Implement an explicit change/revalidation interface with exact old pair/head/generations and fresh competent authority over the complete next permitted pair. Revalidation cannot silently select a successor or spend another assessment right. Changed Profile/evidence scope requires the independently governed evidence/assessment path; O4 must refuse when it is absent. A replacement is another atomic whole-set transition, with immutable prior history and its own authorized consumption. Fence alternate writers to the same settings namespace so they cannot partially overwrite or reopen consumed authority. Preserve legitimate legacy personnel semantics; do not treat an appointment API as a model-settings writer without source evidence.
